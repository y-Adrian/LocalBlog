# 1 具体过程
C/C++ 从源码到可执行文件，一般经历这几个阶段：
```shell
源代码 .c/.cpp
	↓ 预处理 (-E)
预处理文件 .i 
	↓ 编译 (-S)
汇编代码 .s
	↓ 汇编 (-c)
目标文件 .o
	↓ 连接 
可执行文件
```

## 1.1 预处理
预处理过程主要做以下事情：
+ 展开头文件
+ 进行宏替换
+ 处理条件编译
+ 移除注释
+ 为编译器和调试器保留`行/文件`信息

常用命令：
```shell
gcc -E main.c -o main.i
```
## 1.2 编译
将预处理后的 C/C++ 源代码转换成汇编代码，这个过程会进行**语法检查(syntax)**、**语义分析(semantic)**、**类型检查**、**优化**等。
```bash
gcc -S main.i -o main.s
```
生成的 main.s 是汇编代码

## 1.3 汇编
将汇编代码转换成机器码，生成目标文件`.o`。
```bash
gcc -c main.s -o main.o
```

这里的 `.o` 已经是二进制机器码了，但是通常还不能直接运行，因为里面还有未解析的函数或变量引用。

## 1.4 链接
链接器将多个目标文件和库文件合并，解析符号引用，生成最终可执行文件。
```bash
gcc main.o -o main
```

链接阶段主要做：
+ 合并多个 `.o` 文件
+ 查找函数以及全局变量的定义
+ 解析外部符号
+ 分配最终地址
+ 生产可执行 ELF 文件

# 2 实战
## 2.1 源码准备
main.c
```c
#include <stdio.h>

int add(int a, int b);
int main() {
  int a = 10;
  int b = 20;

  int c = add(a, b);
  printf("a + b = %d\n", c);
  return 0;
}
```

add.c
```c
#include <stdint.h>

int add(int a, int b) {
  return a + b;
}
```

## 2.2 预处理
```bash
gcc -E main.c -o main.i
gcc -E add.c -o add.i
```
打开得到的 main.i 和 add.i，可以看到其中内容很多，比如：
```bash
# 0 "main.c"
# 0 "<built-in>"
# 0 "<command-line>"
# 1 "/usr/include/stdc-predef.h" 1 3 4
```

这些不是普通的 C 语句，这些是预处理器生成的行标记。
这些数字的意思为：
+ `# 1`： 行号
+ `"/usr/include/stdc-predef.h"` ： 源文件
- `1`：进入新文件
- `2`：返回之前的文件
- `3`：系统头文件
- `4`：使用 C++ 时内容应该被当做包裹在 `extern "C"` 中

前边得查看到的 `.i` 文件中的前 4 行可以大致理解为：
+ 开始处理 main.c 的内容
+ 处理编译器的内置的宏
+ 处理命令行传入的宏和选项
+ 进入系统头文件

## 2.3 编译
执行以下编译命令：
```bash
gcc -S main.i -o main.s
gcc -S add.i -o add.s
```

查看汇编代码：
main.s:
```asm
;----------------------文件头于伪指令部分
	.arch armv8-a          ;目标架构： ARMv8-A(AArch64)
	.file	"main.c"       ;原文件名，用于调试信息
	.text                  ;进入代码段
	.section	.rodata    ;只读数据段
	.align	3              ;按照 2^3=8 字节对齐
.LC0:
	.string	"a + b = %d\n" ;格式化字符串常量，标号 .LC0
	.text               
	.align	2              ;代码段按照2^2=4字节对齐
	.global	main           ;导出符号 main，链接器可见
	.type	main, %function;生命 main 是一个函数 （ELF符号类型）

;----------------------函数序言，建立栈帧
main:
.LFB0:
	.cfi_startproc           ;开始 CFI（调用帧信息，供调试器/异常展开使用）
	stp	x29, x30, [sp, -32]! ;AArch64特有的成对存储指令，一条指令完成两件事：
	                        ;1、地址预先递减：[sp, -32]!中的！表示pre-indexed（先修改基址寄存器，再访问内存），
	                        ;  即 sp = sp - 32，然后以新的 sp 为基址
	                        ;2、成对存储：把 x29（帧指针）存到[sp+0]，把 x30（链接寄存器LR，即返回地址）存到[sp+8]
	                        ;AArch64栈要求 16 字节对齐，由于后续局部变量也需要用到这块空间
	                        ;这里32是满足对齐且够用的最小值
	                        ;.cfi_*系列指令不生成任何机器码，只是给调试器（gdb）和异常处理机制
	                        ;记录“如何根据当前PC找到上一级栈帧”，可完全忽略，不影响理解程序逻辑
	.cfi_def_cfa_offset 32
	.cfi_offset 29, -32
	.cfi_offset 30, -24
	mov	x29, sp              ;让帧指针 x29 指向当前新栈帧的起始位置，之后函数内对全局变量的寻址都可以使用
	                        ;[x29,#offset]
	                        
;----------------------函数体，变量赋值预调用
	mov	w0, 10
	str	w0, [sp, 20]        ; a = 10， 存到 sp+20
	mov	w0, 20        
	str	w0, [sp, 24]        ; b = 20， 存到 sp+24
	                       ;w0: x0 寄存器的低 32 位视图（AArch64中 w前缀=32位， x前缀=64位，同一屋里寄存器）
	                       ;这里没有开优化，编译器把每个局部变量都实实在在放进栈里，而不是保留在寄存器中
	                       ;因此赋值需要“读到寄存器再写回内存”这种笨拙但直观的方式
	ldr	w1, [sp, 24]        ;取 b 到 w1
	ldr	w0, [sp, 20]        ;取 a 到 w0
	bl	add                 ;调用 add(a,b)
	str	w0, [sp, 28]        ;将返回值存入 c， sp+28
                           ;AArch64的调用约定：
                           ;x0-x7 前8个整型/指针参数；x0同时也是返回值寄存器
                           ;x30（LR) 保存返回地址，由bl自动写入	
                           ;add(a,b)的第一个参数放w0,第二个参数放w1——严格按照约定从左到右依次装入w0,w1,w2...
                           ;bl add(branch with link) = 跳转到add函数，同时把下一条指令地址自动写入x30,这样
                           ;add返回时执行ret就能跳转回来
                           ;add执行完以后按照约定，把返回值放在w0，所以调用后立刻str w0, [sp, 28]把结果存成c
	ldr	w1, [sp, 28]        ;c作为 printf 的第二个参数 -> w1
	adrp	x0, .LC0        ;取 .LC0 所在 4KB 页的基址（高位）
	add	x0, x0, :lo12:.LC0  ;加上页内偏移（低12位），得到完整地址
	                       ;AArch64位的一条指令只有32位的编码空间，塞不下一个完整的64位绝对地址，因此
	                       ;取地址要分两步、用 PC 相对寻址
	                       ;adrp x0, .LC0:计算 .LC0 所在 4KB 页的页地址，把地址高位计算出来，低位清零
	                       ;结果是PC相对的，因此天然支持位置无关代码(PIC)
	                       ;add x0, x0, :lo12:.LC0:把.LC0在页内的低12位偏移量加上去，拼出完整的地址
	                       ;这两条指令组合是AArch64加载全局符号地址的标准范式，凡是访问全局变量、字符串变量、
	                       ;函数指针，都会看到类似的写法
	bl	printf 
	mov	w0, 0               ;return 0; ->返回值放入 w0
	
;----------------------函数尾声，销毁栈帧
	ldp	x29, x30, [sp], 32   ;ldp x29, x30, [sp], 32:与开头的stp ... !对称，成对加载（Load Pair）
	                        ;先从[sp]读回 x29，从[sp+8]读回x30，然后sp=s=+32(post-indexed,先访问再改基址)
	.cfi_restore 30
	.cfi_restore 29
	.cfi_def_cfa_offset 0
	ret                      ;ret 等价 br x30，跳转回 x30中保存的返回地址
	                        ;也就是 bl main（在_start/__libc_start_main）之后的位置
	.cfi_endproc
.LFE0:
	.size	main, .-main
	.ident	"GCC: (Ubuntu 11.4.0-1ubuntu1~22.04.3) 11.4.0"
	.section	.note.GNU-stack,"",@progbits
```

add.s:
```bash
	.arch armv8-a
	.file	"add.c"
	.text
	.align	2
	.global	add
	.type	add, %function
add:
.LFB0:
	.cfi_startproc
	sub	sp, sp, #16
	.cfi_def_cfa_offset 16
	str	w0, [sp, 12]
	str	w1, [sp, 8]
	ldr	w1, [sp, 12]
	ldr	w0, [sp, 8]
	add	w0, w1, w0
	add	sp, sp, 16
	.cfi_def_cfa_offset 0
	ret
	.cfi_endproc
.LFE0:
	.size	add, .-add
	.ident	"GCC: (Ubuntu 11.4.0-1ubuntu1~22.04.3) 11.4.0"
	.section	.note.GNU-stack,"",@progbits
```

## 2.6 问题探究
### 2.6.1 入口函数地址
编译出的二进制，可以通过 `readelf -h main` 查看到程序的入口地址：
```bash
Entry point address:               0x640
```
这个地址真的就是程序实际运行过程中，`_start`函数所在的地址么？

答案是，不一定。
这取决于是否开启了 PIE(Position-Independent Executable)/ASLR(Address Space Layout Randomization地址空间布局随机化)。
对于非 PIE 可执行文件，可以认为我们 readelf 查看到的入口地址，就是该函数在运行时程序地址空间的地址；
对于 PIE 可执行文件， readelf 查看到的入口地址实际只是相对于基址的偏移。运行时程序的基址，是由内核决定的。

查看文件基本信息：

这里提到的 ASLR 是操作系统的一种安全机制，每次程序运行时，内存关键区域地址都会尽量随机变化，如：
+ 程序代码段基址
+ 动态库加载地址
+ 栈地址
+ 堆地址
+ mmap区域地址

ASLR 是地址空间布局随机化，用来让程序每次运行时的内存地址变得不固定；PIR 程序的运行时基址通常由内核根据 ASLR 策略选择，而动态库的具体加载地址通常由动态连接器配合内核完成。
