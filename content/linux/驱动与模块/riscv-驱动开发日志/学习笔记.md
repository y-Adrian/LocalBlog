### 0.1.1 `file_operations` 是字符设备对用户态系统调用的入口表，如果有些自己没有定义对应的接口，用户态调用了系统调用，会发生什么？

如果用户态调用了相关的系统调用，内核中并没有实现，结果取决于该系统调用在 VFS 底层有没有 fallback。

常见情况：
+ 直接返回错误。
+ 走默认辅助逻辑，有些老接口/兼容路径，VFS 会尝试帮你兜底。

### 0.1.2 连续的 poll_wait 会不会阻塞？
`poll_wait(file, &dev->wq, wait); poll_wait(file, &dev->motion_wq, wait);`

poll_wait 本身不会阻塞。poll_wait 的作用更像是：如果用户态这次真的要睡眠，请把这个file和这个等待队列关联起来。

它本身做的是 登记/注册 等待关系，不是立刻睡眠。真正的阻塞发生在上层的 poll/select/epoll 框架中。

### 0.1.4 spin_lock_bh 与 spin_lock 的区别是什么

spin_lock 只拿自旋锁
spin_lock_bh 拿自旋锁之前，先禁止本地 CPU 的 buttom half
spin_lock_irqsave 防止本地 CPU 硬中断

如果进程上下文使用了 spin_lock_bh、spin_lock_irqsave，如果这时候真的需要有中断，是不是就出发不了了？
不是，spin_lock_bh 不会影响硬中断。spin_lock_irqsave 会关闭当前 CPU 的硬中断，但是不是不会触发，只是会被延迟执行，当前 CPU 不会立即执行 ISR

### 0.1.5 `poll()` 里为什么要先 `poll_wait()`，再检查 `ring_empty()`？
poll 要处理两种情况：
+ 当前已经可读
+ 当前不可读，但是未来可能变成可读

先进行 poll_wait 就是先把未来的关系处理好，之后再检查状态，判断当前是否要返回。先登记、再检查。

如果反过来，先检查空不空，再决定要不要 poll_wait，中间有一个竞态窗口：
```shell
CPU0: poll() 检查，发现ring为空
CPU1：write() 写入数据，并 wake_up
CPU0：poll_wait 挂到队列中
```
这种情况下会丢唤醒。

驱动的标准写法就是，先 poll_wait，之后检查设备当前状态，之后返回 mask。poll_wait先把当前进程可等待队列关联起来，避免在状态检查和挂队列之间错过唤醒；随后再检查当前是否就绪，如果就绪直接返回可读掩码。
