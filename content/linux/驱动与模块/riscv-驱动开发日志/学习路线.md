## 1.3 Phase 1：Linux 内核驱动开发（第 2–4 周）

> 这是整个 JD 的核心，花时间最多，动手最多。

### 1.3.1 字符设备驱动（第 2 周）

#### 1.3.1.1 学习目标

- 能独立编写一个完整的字符设备驱动，包含 open / read / write / ioctl
- 理解内核空间与用户空间的数据交换（`copy_to_user` / `copy_from_user`）
- 理解设备号（主/次设备号）的分配与管理

#### 1.3.1.2 核心知识点

```c
// 驱动的最小骨架
#include <linux/module.h>
#include <linux/fs.h>
#include <linux/cdev.h>

static struct file_operations fops = {
    .owner   = THIS_MODULE,
    .open    = my_open,
    .read    = my_read,
    .write   = my_write,
    .release = my_release,
    .unlocked_ioctl = my_ioctl,
};

module_init(my_init);   // 加载时调用
module_exit(my_exit);   // 卸载时调用
MODULE_LICENSE("GPL");
```

关键 API 清单：

|功能|API|
|---|---|
|动态申请设备号|`alloc_chrdev_region()`|
|注册字符设备|`cdev_init()` + `cdev_add()`|
|创建 /dev 节点|`class_create()` + `device_create()`|
|用户态数据拷贝|`copy_to_user()` / `copy_from_user()`|
|内核内存分配|`kmalloc()` / `kfree()`|

#### 1.3.1.3 实战练习（在 Duo S 上完成）

**练习 1**：写一个虚拟字符设备，用 `cat /dev/mydev` 返回一段固定字符串。  
**练习 2**：支持 `echo "hello" > /dev/mydev`，驱动将数据存入内核缓冲区，再读出。  
**练习 3**：增加 ioctl 命令，支持用户态程序控制驱动行为（如清空缓冲区）。

#### 1.3.1.4 面试高频问题

> **Q: copy_to_user 和直接 memcpy 有什么区别？**  
> 关键点：用户态地址可能无效或触发缺页，copy_to_user 会做地址合法性校验并处理缺页中断，直接 memcpy 在内核中访问用户态地址可能导致 oops。

> **Q: 内核模块加载时发生了什么？**  
> 关键点：`insmod` → 内核调用 `load_module()` → ELF 重定位 → 执行 `module_init` 指定的函数 → 注册到内核模块链表。

> **Q: 主设备号和次设备号的作用分别是什么？**  
> 关键点：主设备号标识驱动程序，次设备号标识具体设备实例。内核通过主设备号找到对应的 `file_operations`。

### 1.3.2 中断处理（第 3 周前半）

#### 1.3.2.1 学习目标

- 能注册和处理硬件中断
- 理解上半部（hardirq）和下半部（softirq / tasklet / workqueue）的区别与选用

#### 1.3.2.2 核心知识点

```c
// 注册中断
ret = request_irq(irq_num, my_irq_handler,
                  IRQF_TRIGGER_RISING, "my_irq", dev);

// 上半部：快速、原子，不能睡眠
irqreturn_t my_irq_handler(int irq, void *dev_id) {
    // 读取硬件状态、清中断标志
    tasklet_schedule(&my_tasklet);  // 触发下半部
    return IRQ_HANDLED;
}

// 下半部（tasklet）：可延迟，仍不能睡眠
void my_tasklet_func(unsigned long data) { /* 耗时处理 */ }

// 下半部（workqueue）：可以睡眠，可调度
INIT_WORK(&my_work, my_work_func);
schedule_work(&my_work);
```

#### 1.3.2.3 面试高频问题

> **Q: tasklet 和 workqueue 怎么选？**  
> 关键点：tasklet 运行在软中断上下文，不能睡眠，适合简单快速处理；workqueue 运行在内核线程，可以睡眠，适合需要等待 I/O 或持有互斥锁的场景。

> **Q: 中断上半部为什么要尽量短？**  
> 关键点：上半部运行时中断被屏蔽（取决于 IRQF_DISABLED），长时间占用会导致其他中断响应延迟，影响系统实时性。

### 1.3.3 内存管理与 DMA 基础（第 3 周后半）

#### 1.3.3.1 学习目标

- 理解内核虚拟地址空间布局
- 能正确使用 `ioremap` 访问硬件寄存器
- 了解 DMA 的基本概念和一致性问题

#### 1.3.3.2 核心知识点

```c
// MMIO 寄存器访问
void __iomem *base = ioremap(phys_addr, size);
u32 val = readl(base + REG_OFFSET);
writel(val | BIT(3), base + REG_CTRL);
iounmap(base);

// 内存屏障（重要！）
rmb();  // 读屏障
wmb();  // 写屏障
mb();   // 读写屏障
```

内核内存分配对比：

|API|特点|适用场景|
|---|---|---|
|`kmalloc`|物理连续，小块，不可睡眠（GFP_ATOMIC）|中断上下文、小内存|
|`vmalloc`|虚拟连续，物理可不连续|大块内存，可睡眠|
|`get_free_pages`|按页分配，物理连续|DMA 缓冲区|
|`dma_alloc_coherent`|DMA 专用，一致性保证|设备 DMA 操作|

#### 1.3.3.3 面试高频问题

> **Q: ioremap 和普通 kmalloc 的区别？**  
> 关键点：ioremap 将物理地址（通常是设备寄存器的物理地址）映射到内核虚拟地址空间，不分配新物理内存；kmalloc 从内核内存池分配新物理内存。

> **Q: 为什么访问 MMIO 寄存器要加内存屏障？**  
> 关键点：编译器和 CPU 可能对访问顺序进行优化重排，对硬件寄存器的访问必须严格按序。`readl`/`writel` 本身包含屏障语义，但在多个操作之间有时仍需显式屏障。

### 1.3.4 内核同步机制（第 4 周）

#### 1.3.4.1 学习目标

- 掌握自旋锁、互斥锁、读写锁的使用场景
- 理解原子操作
- 能分析简单的死锁场景

#### 1.3.4.2 核心知识点

```c
// 自旋锁（不可睡眠，适合中断上下文）
spinlock_t lock;
spin_lock_init(&lock);
spin_lock_irqsave(&lock, flags);   // 关中断+加锁
/* 临界区 */
spin_unlock_irqrestore(&lock, flags);

// 互斥锁（可睡眠，不可用于中断上下文）
struct mutex mtx;
mutex_init(&mtx);
mutex_lock(&mtx);
/* 临界区 */
mutex_unlock(&mtx);

// 原子操作
atomic_t counter = ATOMIC_INIT(0);
atomic_inc(&counter);
int val = atomic_read(&counter);
```

#### 1.3.4.3 面试高频问题

> **Q: 自旋锁和互斥锁怎么选？**  
> 关键点：中断上下文只能用自旋锁（不能睡眠）；临界区很短（微秒级）用自旋锁更高效；临界区可能睡眠（如 I/O 等待）必须用互斥锁。

> **Q: 在中断处理函数中可以使用 mutex_lock 吗？**  
> 关键点：不可以。中断上下文不能睡眠，mutex_lock 可能导致睡眠等待，会触发 "scheduling while atomic" BUG。

## 1.4 Phase 2：RISC-V 架构（第 5–6 周）

> 教程长文：[[linux/学习路径/RISC-V 特权模式与 OpenSBI]]（与下文提纲对照复习）。

### 1.4.1 特权架构与寄存器（第 5 周）

#### 1.4.1.1 学习目标

- 理解 RISC-V 三种特权模式（M/S/U）的含义和切换
- 能读懂 CV1800B 的启动日志，理解 OpenSBI 的角色
- 掌握常用 CSR 寄存器的作用

#### 1.4.1.2 核心知识点

**三种特权模式**：

```
Machine Mode (M)     最高权限，运行 OpenSBI / bootloader
Supervisor Mode (S)  运行 Linux 内核
User Mode (U)        运行用户态程序
```

**关键 CSR 寄存器**：

|CSR|作用|
|---|---|
|`mstatus` / `sstatus`|全局中断使能、特权模式状态|
|`mtvec` / `stvec`|异常/中断向量基地址|
|`mepc` / `sepc`|异常发生时保存的 PC|
|`mcause` / `scause`|异常原因编码|
|`satp`|页表基地址 + 地址翻译模式（Sv39/Sv48）|
|`medeleg` / `mideleg`|将异常/中断委托给 S 模式处理|

```c
// 内联汇编读写 CSR
#define csr_read(csr)                       \
({                                          \
    register unsigned long __v;             \
    __asm__ volatile ("csrr %0, " #csr      \
                      : "=r" (__v));        \
    __v;                                    \
})
```

#### 1.4.1.3 面试高频问题

> **Q: OpenSBI 是什么，在 RISC-V 启动中的作用？**  
> 关键点：OpenSBI（Supervisor Binary Interface）运行在 M-Mode，为 S-Mode（内核）提供统一的硬件调用接口（类似 BIOS/UEFI 在 x86 的角色），屏蔽不同厂商 M-Mode 实现差异。内核通过 `ecall` 调用 SBI 服务。

> **Q: RISC-V 的异常处理流程是什么？**  
> 关键点：异常发生 → 保存 PC 到 `sepc`，原因写入 `scause` → 跳转到 `stvec` 指向的处理函数 → 处理完毕执行 `sret` 返回（从 `sepc` 恢复执行）。

### 1.4.2 RISC-V 汇编与 Linux 内核适配（第 6 周）

#### 1.4.2.1 学习目标

- 能读懂 RISC-V 汇编代码（内核 entry.S、启动代码）
- 理解 RISC-V Linux 内核的内存布局
- 了解 RISC-V 架构适配的主要工作内容

#### 1.4.2.2 核心知识点

**常用汇编指令**：

```asm
# 寄存器操作
li   a0, 42          # 加载立即数
mv   a1, a0          # 寄存器间移动
la   t0, symbol      # 加载地址

# 内存访问
lw   a0, 0(sp)       # 从内存加载（word）
sw   a0, 0(sp)       # 存储到内存
ld   a0, 0(sp)       # 64 位加载（doubleword）

# 控制流
jal  ra, func        # 跳转并保存返回地址
jalr zero, 0(ra)     # 返回（ret 伪指令）
beq  a0, a1, label   # 条件跳转

# 系统调用
ecall                # 陷入更高特权模式
```

**架构适配的主要工作**：

- 新 SoC 的 `arch/riscv/` 相关文件修改
- 设备树（`.dts`）编写和调试
- 早期串口（earlycon）适配，让内核启动时就能打印
- 时钟、中断控制器（PLIC）的驱动适配

#### 1.4.2.3 实战练习

在 Duo S 上：

1. 读懂 `arch/riscv/kernel/entry.S` 的异常入口代码
2. 用内联汇编写一个读取 `cycle` CSR 的函数并在驱动中调用

#### 1.4.2.4 面试高频问题

> **Q: RISC-V 和 ARM/x86 在内核适配上最大的区别是什么？**  
> 关键点：RISC-V 没有厂商统一的中断控制器标准（ARM 有 GIC），PLIC 是标准中断控制器但 SoC 实现有差异；SBI 层屏蔽了 M-Mode 差异；设备树是描述硬件的唯一方式（无 ACPI 支持）。

## 1.5 Phase 3：设备树与总线框架（第 7–8 周）

### 1.5.1 设备树（Device Tree）（第 7 周）

#### 1.5.1.1 学习目标

- 能独立编写简单的设备树节点
- 理解 `compatible` 匹配机制
- 能修改 Duo S 的 DTS 并重新编译

#### 1.5.1.2 核心知识点

```dts
// 设备树节点示例
my_device: my-device@10000000 {
    compatible = "myvendor,mydevice";    // 驱动匹配关键字
    reg = <0x0 0x10000000 0x0 0x1000>;  // 寄存器物理地址和大小
    interrupts = <0 32 4>;              // 中断号
    clocks = <&clk_gate 5>;             // 时钟依赖
    status = "okay";                    // 使能节点
};
```

关键属性说明：

|属性|说明|
|---|---|
|`compatible`|字符串列表，内核用于匹配驱动，格式 `"vendor,model"`|
|`reg`|寄存器地址空间，格式由父节点的 `#address-cells` 决定|
|`interrupts`|中断描述，格式由中断控制器的 `#interrupt-cells` 决定|
|`status`|`"okay"` 表示使能，`"disabled"` 表示禁用|
|`clocks`|引用时钟节点的 phandle|

#### 1.5.1.3 实战练习

1. 在 Duo S 的 DTS 中添加一个自定义节点
2. 编写 platform driver，通过 `of_match_table` 匹配该节点
3. 在 `probe` 函数中用 `platform_get_resource` 获取 reg 资源并 ioremap

#### 1.5.1.4 面试高频问题

> **Q: 驱动是如何与设备树节点匹配的？**  
> 关键点：驱动在 `of_match_table` 中声明支持的 compatible 字符串 → 内核解析 DTB 时为每个 status=okay 的节点创建 platform_device → platform_bus 遍历已注册驱动，比较 compatible → 匹配成功则调用驱动的 `probe` 函数。

> **Q: 设备树中的 phandle 是什么？**  
> 关键点：phandle 是设备树节点的唯一整数标识符，用于节点间的引用（如时钟、中断控制器引用）。`clocks = <&clk 5>` 中 `&clk` 就是对 clk 节点 phandle 的引用。

### 1.5.2 Platform Driver 与 I²C/SPI 框架（第 8 周）

#### 1.5.2.1 学习目标

- 熟练掌握 platform driver 框架
- 了解 I²C / SPI 子系统的驱动模型
- 能读懂一个完整的 I²C 设备驱动

#### 1.5.2.2 Platform Driver 核心框架

```c
static int my_probe(struct platform_device *pdev)
{
    struct resource *res;
    void __iomem *base;

    res = platform_get_resource(pdev, IORESOURCE_MEM, 0);
    base = devm_ioremap_resource(&pdev->dev, res);  // 推荐用 devm_ 系列
    if (IS_ERR(base))
        return PTR_ERR(base);

    // 初始化硬件 ...
    return 0;
}

static int my_remove(struct platform_device *pdev)
{
    // devm_ 管理的资源会自动释放
    return 0;
}

static const struct of_device_id my_of_match[] = {
    { .compatible = "myvendor,mydevice" },
    { }  // 末尾必须有空条目
};
MODULE_DEVICE_TABLE(of, my_of_match);

static struct platform_driver my_driver = {
    .probe  = my_probe,
    .remove = my_remove,
    .driver = {
        .name           = "my-device",
        .of_match_table = my_of_match,
    },
};
module_platform_driver(my_driver);  // 自动生成 init/exit
```

**`devm_` 系列 API 的重要性**：  
资源由设备生命周期管理，`remove` 时自动释放，避免内存泄漏。**面试中主动提到这点会加分。**

#### 1.5.2.3 面试高频问题

> **Q: probe 函数什么时候被调用，如果返回 -EPROBE_DEFER 会发生什么？**  
> 关键点：当驱动与设备匹配时调用 probe。返回 `-EPROBE_DEFER` 表示依赖的资源（如时钟、GPIO）还未就绪，内核会在稍后重试 probe，这是处理初始化顺序依赖的标准方法。

## 1.6 Phase 4：虚拟化基础（第 9 周）

### 1.6.1 学习目标

- 理解 Hypervisor 的两种类型及应用场景
- 了解 RISC-V H 扩展的基本原理
- 能在面试中清楚解释虚拟化的基本概念

### 1.6.2 核心知识点

**Hypervisor 类型**：

```
Type-1（裸机型）                Type-2（托管型）
+-----------+                  +-----------+
|  Guest OS |                  |  Guest OS |
+-----------+                  +-----------+
| Hypervisor|                  |   KVM/    |
|  (直接运行)|                  | QEMU-KVM  |
+-----------+                  +-----------+
|  硬件      |                  |  Host OS  |
+-----------+                  +-----------+
                                |  硬件      |
 示例：Xen, VMware ESXi         +-----------+
                                 示例：KVM, VirtualBox
```

**RISC-V H 扩展关键概念**：

|概念|说明|
|---|---|
|VS-Mode|虚拟化 Supervisor Mode，Guest OS 运行的模式|
|VU-Mode|虚拟化 User Mode，Guest 用户进程运行的模式|
|HS-Mode|Host Supervisor Mode，Hypervisor 运行的模式|
|`hstatus`|H 扩展新增的 CSR，控制虚拟化行为|
|`hgatp`|Guest 物理地址到 Host 物理地址的二级页表基地址|
|`VMID`|虚拟机标识，类似进程的 ASID|

**两阶段地址翻译（Two-Stage Address Translation）**：

```
Guest VA → (VS-Mode 页表, satp) → Guest PA
Guest PA → (HS-Mode 页表, hgatp) → Host PA
```

这是 RISC-V 虚拟化的核心机制，面试时能画出这个图即可。

### 1.6.3 面试高频问题

> **Q: 虚拟化中的 VM-Exit 是什么？**  
> 关键点：Guest OS 执行特权操作（访问物理硬件、执行 `ecall`）时，会触发陷入（trap）到 Hypervisor，称为 VM-Exit。Hypervisor 模拟该操作后，通过 `sret` 返回 Guest，称为 VM-Entry。频繁的 VM-Exit 是虚拟化性能开销的主要来源。

> **Q: 直通（Passthrough）和模拟（Emulation）有什么区别？**  
> 关键点：Passthrough（借助 IOMMU/VFIO）让 Guest 直接访问物理硬件，性能接近原生；Emulation 由 Hypervisor 软件模拟设备行为，灵活但有性能开销。
